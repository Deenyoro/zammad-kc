# Maintaining the KC fork

How this fork is organised and the rules for changing it.

## Project Overview

Zammad is an open-source helpdesk/customer support platform built on Rails 8.0 (Ruby 3.4.7, Node 22, PostgreSQL 17). It has two modern Vue 3 frontends (desktop-view and mobile) and one legacy desktop-app under `app/assets/`. This is the KawaConnect fork, which uses a KC overlay system (`kc/` directory) for custom code isolation, all KC code is copied into the Zammad app tree at Docker build time using `rsync --ignore-existing`, so upstream updates merge cleanly with zero application code conflicts.

## Architecture

### Three Frontend Apps

| App | Path | Stack | API |
|-----|------|-------|-----|
| desktop-app (legacy) | `app/assets/` | CoffeeScript, Spine.js, Sprockets | REST |
| desktop-view (new) | `app/frontend/apps/desktop/` | Vue 3, TypeScript, Pinia, TailwindCSS v4 | GraphQL |
| mobile | `app/frontend/apps/mobile/` | Vue 3, TypeScript, Pinia, TailwindCSS v4 | GraphQL |

Shared frontend code lives in `app/frontend/shared/`. ESLint enforces that desktop and mobile apps never cross-import, both import only from `#shared`. Path aliases are in `tsconfig.base.json`.

### GraphQL Schema (Auto-Discovery)

- Entry points (`app/graphql/gql/entry_points/`) dynamically discover all descendants via `eager_load_recursive`
- Queries extend `Gql::Queries::BaseQuery`, mutations extend `Gql::Mutations::BaseMutation`
- Schema field names are auto-derived from class names (`graphql_field_name`)
- Mutations return errors via `error_response()` as `[UserErrorType]` arrays
- Frontend operations in `app/frontend/shared/graphql/` with `.api.ts` and `.mocks.ts` files, auto-generated by `pnpm generate-graphql-api`

### Authorization Stack

Multi-layer: GraphQL declarations → Pundit policies → field-level filtering.
- GraphQL layer: `requires_authentication`, `requires_permission(*perms)` class methods
- Policy layer (`app/policies/`): `ApplicationPolicy` with Pundit; `FieldScope` for field-level allow/deny
- User context threading: `UserInfo.with_user_id(user_id) { block }` used in resolvers, jobs, and services

### Service Object Pattern

`app/services/service/` contains business logic: `Service::Base` (override `execute()`) and `Service::BaseWithCurrentUser` (injects `current_user:`). Called from mutations, controllers, and jobs.

### Background Jobs

`app/jobs/`, `ApplicationJob` subclasses processed by Delayed Job. Jobs use `UserInfo.with_user_id()` when user context is needed.

### Key Directories (non-standard)

- `app/services/service/`: Service objects encapsulating business logic
- `app/graphql/gql/`: GraphQL schema, types, mutations, subscriptions
- `app/policies/`: Authorization policies (Pundit)
- `app/frontend/apps/desktop/`: Vue 3 desktop app
- `app/frontend/apps/mobile/`: Vue 3 mobile app
- `app/frontend/shared/`: Shared Vue components, composables, stores, GraphQL types, form system
- `app/assets/javascripts/`: CoffeeScript frontend (Spine + jQuery, legacy, still actively maintained)
- `lib/`: Library code, prefer minimal Rails coupling

## General Guidelines

- All new files must include the Zammad copyright header.
- Never edit translation files (`i18n/*.po`) directly, translations are managed via translations.zammad.org.

## KC Overlay System

See `kc/README.md` for the full developer guide with examples.

### How It Works

All custom code lives in `kc/`. During Docker build, two scripts run in sequence:

1. `kc/script/apply-overlay.sh`: copies NEW files into the Zammad app tree using `rsync --ignore-existing` (never overwrites upstream files, includes collision detection that aborts on conflicts).
2. `kc/script/apply-patches.sh`: applies unified diffs from `kc/patches/` to EXISTING upstream files (for features like BCC, "Send with text color", and bulk merge that must modify upstream frontend code). If a patch fails to apply (e.g., upstream changed the file), the build fails loudly.

`kc/script/heal-patches.sh` re-anchors a patch that no longer applies exactly: `git apply --3way` first, fuzzy `patch` as last resort, then it rewrites the patch file as an exact diff. Only a true conflict (upstream rewrote the very lines a patch changes) cannot be healed. The two pipelines use it differently:

- **GitLab (`kc/gitlab-ci.yml`, the pipeline that builds the released image):** the `verify-patches` job runs the script and fails if it had to change anything. CI never writes to the repo. Run `bash kc/script/heal-patches.sh` locally, review the diff in `kc/patches/`, commit it.
- **GitHub (`.github/workflows/build-and-push.yml`, on the mirror):** runs the script with `HEAL_PUSH_BRANCH` set, so healed patches are committed and pushed back to the branch by the workflow.

The `kc/` directory is deleted from the final image.

| Layer | Mechanism |
|-------|-----------|
| Models | `ActiveSupport::Concern` + `prepend` registered in `kc/config/initializers/kc_loader.rb` |
| Controllers & Services | `Kc::` namespace, autoloaded by Rails |
| Routes | `kc/config/routes/kc_routes.rb` auto-discovered by Zammad's route glob |
| Legacy Frontend | CoffeeScript controllers registered via `App.Config.set` |
| Modern Frontend | Vite `import.meta.glob` discovers `pages/kc/routes.ts` |
| Frontend Patches | Unified diffs in `kc/patches/` applied at build time via `apply-patches.sh` |
| Gems | `kc/Gemfile.local` loaded natively by Zammad's `Gemfile` |
| Migrations | Standard Rails migrations in `kc/db/migrate/` |
| Deploy configs | `kc/deploy/`, docker-compose.yml and .env.example (not copied to app tree) |

### KC Tests and CI

`kc/gitlab-ci.yml` is the pipeline for this fork (the GitLab project's CI configuration file setting points at it; upstream's root `.gitlab-ci.yml` is not used). It runs on pushes to `develop`, on `v*` tags and on manual or API runs. Jobs, with the command to run each one locally from the repository root:

| Job | What it checks | Local command |
|-----|----------------|---------------|
| `verify-patches` | every `kc/patches/*.patch` applies exactly | `bash kc/script/heal-patches.sh && git diff --stat -- kc/patches` (no output = pass) |
| `test-conversation-reopen` | 15-minute reopen window (standalone, sqlite) | `ruby kc/test/recent_conversation_reopen_test.rb` |
| `verify-sms-blocklist` | SMS ticket blocklist | `rspec --options /dev/null kc/spec/unit/sms_ticket_blocklist_spec.rb` |
| `verify-graph-read-mail` | read mail import | `rspec --options /dev/null kc/spec/unit/microsoft_graph_inbound_read_mail_spec.rb` |
| `verify-group-chats` | group text and group chat tickets | `rspec --options /dev/null kc/spec/unit/group_chats_spec.rb` |
| `verify-frontend-load-order` | legacy CoffeeScript uses no `lib/app_post` class at load time | `python3 kc/script/check-frontend-load-order.py .` |
| `build` | Docker image (overlay, patches, asset compile) | needs all jobs above |
| `boot-test-legacy-ui` | the compiled legacy bundle from the built image loads in headless Chromium without an error | needs the built image |

The gem versions the standalone jobs install are listed in `kc/gitlab-ci.yml`. A full pipeline takes well over an hour, most of it the image build.

Not run by CI: the other specs under `kc/spec/` (`requests/`, `services/`, `models/`, `jobs/`, `graphql/`, `lib/`) load `rails_helper`, and the Vitest specs under `kc/app/frontend/**/__tests__/` need the frontend toolchain. `spec/` is not one of the overlaid directories, so these only run in a Zammad development checkout that has the overlay and patches applied and the spec files copied next to upstream's (see "Testing" above for the upstream commands). Run the ones for the area you change before pushing, and do not read a green pipeline as proof that they pass.

### Syncing Upstream

History is merge-only: never rebase or rewrite upstream commits.

```bash
git remote add upstream https://github.com/zammad/zammad.git   # once
kc/script/check-sync-safety.sh --fetch     # exit 0 = the merge will be clean
git merge upstream/develop
bash kc/script/heal-patches.sh             # re-anchor drifted patches, review the diff in kc/patches/
kc/script/check-sync-safety.sh
```

Then add a `kc/CHANGELOG.md` entry (upstream range, new migrations, what changed in the patches), commit and push. `kc/script/sync-canary.sh` simulates the next sync in a throwaway worktree without touching yours: the merge, every patch, overlay path collisions, and the upstream methods KC concerns override (`kc/upstream-fingerprints.txt`; add a line there when a new concern overrides an upstream method). The GitHub mirror runs it daily (`sync-canary.yml`) and opens an issue when the next sync needs manual work.

### Current KC Features

- **Microsoft Teams Chat**: Bidirectional messaging (Graph API, OAuth2, webhooks + backup polling, directory sync). Admin at System > KC - Teams Chat. Group and meeting chats are titled after the chat (`Kc::TeamsChatTitle`): "Teams group chat: <topic>", or the members' names when nobody set a topic (optional Setting `kc_teams_chat_group_ticket_title_template`, `{chat_name}`). The generated title is remembered in `preferences.teams_chat.auto_title` and follows topic/member changes (on each message and on each poll of the chat); a title an agent typed is never replaced. `Kc::BackfillGroupChatTitlesJob.new.perform(dry_run:, include_closed:)` retitles older tickets (Teams and RingCentral group texts).
- **RingCentral SMS/MMS**: Bidirectional SMS (OAuth2, webhooks + backup polling, missed call tracking). Admin at System > KC - RingCentral SMS. Texts sent from the RingCentral app are captured as internal notes (with MMS attachments); agent-initiated conversations get a ticket. `Kc::BackfillRingcentralSmsJob.new.perform(days:, dry_run:)` re-files a gap from the message store. Calls to or from a number with an open SMS ticket (RingCentral or FreePBX, either direction) are added to that ticket as internal notes without changing its state (`kc_ringcentral_sms_call_thread_notes`); a RingCentral call is noted on the next 5-minute poll, before its record settles, and a thread closed after the call started still gets the note. One note per call (message id `kc_call_note:<call key>`, plus a 3-minute cross-source check under a ticket row lock). Group texts are one ticket per group: matched only on the full participant set (never a member's 1:1 ticket), titled "Group SMS: <members>" (optional Setting `kc_ringcentral_sms_group_ticket_title_template`, `{participants}`), `preferences.ringcentral_sms.group: true`, and agent replies go to every participant. Company extension numbers in a message's recipients are ignored (`Kc::RingcentralApi.textable_number?`).
- **FreePBX Phone & SMS**: Connection to the KC PBX connector on the FreePBX host (bearer token, no OAuth). Missed-call tickets and auto-reply texts, call history as closed tickets, escalation calls, health check. Text messaging (`kc_freepbx_sms_enabled`, off by default) mirrors RingCentral SMS: inbound texts open/continue tickets (article type `freepbx_sms_message`, conversation keys, thread window, context note), agent replies and MMS go out through the connector, texts sent from UCP/Sangoma Connect are captured as notes, webhook (`/api/v1/kc/freepbx_sms_webhook`, `X-KC-Token`) plus per-minute polling, "New SMS Message (FreePBX)" in the + menu only while enabled, PBX numbers usable as auto-reply senders. Connector contract in `kc/deploy/freepbx-connector-sms.md`. `Kc::BackfillFreepbxSmsJob.new.perform(days:, dry_run:)` re-files a gap. Admin at System > KC - FreePBX.
- **Contact Names on SMS**: `Kc::PhoneContacts` puts a name next to the number: SMS ticket titles ("SMS from Jane Smith (+14125550100)"), the From of customer texts, the To of captured texts and call notes. Lookup order: Zammad user by phone/mobile (incl. Microsoft 365 directory imports; last-ten-digit match), RingCentral address book, FreePBX phonebook (`GET /contacts` on the connector, optional). Placeholder customers (named after their number) are renamed after the contact. `Kc::BackfillSmsContactNamesJob.new.perform(dry_run:, users:)` updates open SMS tickets (closed ones are left alone).
- **RingCentral Contact Sync**: `Kc::RingcentralContactSync` (service) and `Kc::RingcentralContactSyncJob`, every 6 hours ("Sync RingCentral contacts." scheduler, `perform_later`) and from the "Sync contacts now" button per account. Two switches per RingCentral channel, both off by default, set in the account's Edit dialog: `options.contact_import` and `options.contact_export`. Import: address-book contacts with a name and a number or email become customers or are matched to a user (remembered contact id, then email, then phone/mobile on the last ten digits; several named users on the numbers = skipped); placeholder users get the contact's name, other users only get blank fields filled (names and emails set by people or the directory are never overwritten); an existing organization named exactly like the contact's company is linked, none are created. Export: every active user with a `microsoft_teams` authorization (all tenants) and a phone or mobile gets a contact (firstName, lastName, company = organization, email, mobile → mobilePhone, phone → businessPhone, notes "Synced from Zammad directory…"), updated when those change; a contact staff made for the same number is only recorded, never changed or duplicated; a synced contact whose notes marker staff removed, or that staff deleted, is left alone from then on. Nothing is deleted in RingCentral, contacts of users deactivated later stay as they are. Import skips contacts with the marker, so the two directions never loop. State per user in `preferences.kc_ringcentral_contacts[<channel id>]` (`contact_id`, `origin` import/export/manual/deleted, `fingerprint`); last run stats and the last error in `channel.options.last_contact_sync`, shown on the admin page. Writes are spaced 6.5 s apart (RingCentral "Heavy" group, 10 a minute), capped at 150 a run; a 429 waits for Retry-After once (up to 60 s), otherwise the rest follow on the next run. A 403 (missing Contacts permission) stops the export with a message on the admin page.
- **Email BCC**: `ticket_articles.bcc` column; BCC recipients go out in the envelope only (`Kc::EmailJobBcc` → `Kc::EmailOutboundBcc`; `Kc::MicrosoftGraphBccInMime` for Graph). Legacy UI: `kc_bcc_field.coffee` (always shown for email). New desktop/mobile: `useTicketEditForm-bcc.patch` puts the `bcc` recipient field in the `article` group right after CC (desktop: hidden behind an "Add BCC" link on the CC row, like upstream's "Add CC"; mobile: always shown), `useTicketEdit.patch` sends `article.bcc` with `ticketUpdate`, `kc_article_bcc.rb` adds the GraphQL argument (frontend types + test introspection in `graphql-types-bcc.patch`). `kc_bcc_access` (all/admin/disabled) gates the field in both UIs. Scheduled replies keep `bcc` (controller + `Kc::ExecuteScheduledArticle` allowlists).
- **Read Mail Import (Microsoft 365)**: With "keep messages on server" upstream fetches only unread mail, so a message someone opened in Outlook before the next fetch was never imported. `Kc::MicrosoftGraphInboundReadMail` also lists read mail of the channel's folder received in the last `KC_GRAPH_READ_MAIL_WINDOW_HOURS` (default 72, max 336, `0` = off) and imports those whose Message-ID no article has yet (stricter than upstream's per-channel check, so mail Zammad sent is not re-imported). Processed Graph message ids are remembered in Rails.cache (memcached) for the window + 1 day, so a deleted ticket or a filtered message does not come back each fetch; a memcached restart only loses that memory.
- **Per-Agent Time Tracking**: Enhanced time accounting with agent attribution, sidebar widget, admin reporting with Excel export.
- **Scheduled Replies**: Queue articles for future delivery (`Kc::ScheduledArticle`, `Kc::SendScheduledArticlesJob` every minute, `Kc::ExecuteScheduledArticle`). Legacy UI: "Schedule Reply" in the Update menu, datetime modal, timeline banner with Edit/Cancel. New UI: "Scheduled Replies" sidebar (tab badge = pending count; no timeline banner, that would need an upstream patch). At schedule time the selected files of the compose form's UploadCache are copied into Store items owned by the record (object `Kc::ScheduledArticle`, o_id = record id) and `form_id` is dropped, so files added to the form later are never sent and the monthly UploadCache purge cannot lose them; the copies are removed when the record leaves `pending`. New-UI requests pass `attachments: [{name, type}]` (only those files are taken); without it (legacy) every non-inline file of the form is taken. "Edit" = `DELETE ...?restore_form_id=<compose form id>`: cancels and copies the files back into that form. Records from before stored copies still send from their numeric legacy form_id. The new UI sends `content_type` from the reply editor (text/plain for SMS/Teams) and runs HTML through `transformEditorHtml` like upstream's processArticle.
- **Waiting for Reply State**: Custom ticket state that auto-transitions to "open" on customer reply.
- **Closed (Locked) States**: Ticket states that prevent customer reopens (permanent and timed variants).
- **API Health Check**: Proactive monitoring of external API connections (runs every 5 min, auto-creates/closes alert tickets).
- **New Conversation Initiators**: Agent-facing UI for starting SMS and Teams conversations from scratch. In both desktop UIs the Group selector starts on "Default (channel group)" (empty `group_id` = the channel's group) and lists only active groups the agent may create tickets in (legacy: `App.User#allGroupIds('create')`; Vue: `GET /api/v1/kc/conversations/groups`); only active channels are offered as sender. Every "+ New SMS/Teams Message" opens a draft taskbar tab (pen icon, like New Ticket) in BOTH desktop UIs: same task key (`KcNewSmsScreen-<id>`, `KcNewFreepbxSmsScreen-<id>`, `KcNewTeamsScreen-<id>`), callback (`KcNew{Sms,FreepbxSms,Teams}ConversationContent`) and state field names, so a draft started in one UI is listed and restored in the other. `Kc::TaskbarConversationDraftEntities` adds the callbacks to `Taskbar.taskbar_entities` (and so to the GraphQL `TaskbarEntityType` enum, built at class load - the prepend runs in `to_prepare`, before eager loading). Vue (desktop/mobile): the reply form keeps the text when the type is switched; an existing internal note additionally offers "Send as email reply" (new email reply to the customer with the note's text).

### KC Coding Patterns

**Naming conventions:**
- Ruby classes: `Kc::` namespace (e.g., `Kc::ScheduledArticle`, `Kc::ApiHealthCheckService`)
- Database tables: `kc_` prefix (e.g., `kc_scheduled_articles`)
- Routes: scoped under `/api/v1/kc/`
- Methods added to upstream models via concerns: `kc_` prefix (e.g., `kc_full_display_name`)
- Migration classes: prefixed with `CreateKc`, `AddKc`, etc.

**Defensive programming, all KC code must survive upstream changes:**
```ruby
# Safe constantize before use
graph_class = 'Kc::MicrosoftTeamsGraph'.safe_constantize
return if graph_class.nil?

# Safe table/column checks in models
if table_exists? && column_names.include?('agent_id')
  belongs_to :agent
end

# Safe prepend with error handling in kc_loader.rb
kc_prepend = lambda do |target_str, concern_str|
  target  = target_str.safe_constantize
  concern = concern_str.safe_constantize
  return Rails.logger.warn("KC: Skipping #{concern_str}") unless target && concern
  target.prepend(concern)
end
```

**Authorization:** Every KC controller has a Pundit policy at `kc/app/policies/controllers/kc/` using `default_permit!('admin')` or `default_permit!('ticket.agent')`, and `prepend_before_action :authenticate_and_authorize!`.

**Background jobs:** Use `retry_on StandardError, wait: 10.seconds, attempts: 3`. Track delivery status in `article.preferences` (e.g., `article.preferences[:teams_chat][:delivery_status]`).

**Token management:** Refresh tokens proactively in health check job. Persist with `channel.with_lock { ... }` to avoid race conditions. Use `Transaction.execute(reset_user_id: true, context: 'channel_name')` for ticket/article creation.

**Migrations:** Guard with `return if !Setting.exists?(name: 'system_init_done')`. Use idempotent patterns (`create_if_not_exists`, `column_exists?`, `table_exists?`).

**Legacy frontend (CoffeeScript):** Controllers extend `App.Controller` or `App.ControllerModal`. Templates are `.jst.eco` files. Navigation registered via `App.Config.set('KcFeatureName', { prio: N, ... })`. Settings accessed via `App.Setting.get('kc_setting_name')`.

**Frontend patches:** When KC must modify an existing upstream TypeScript/Vue file (no `prepend` equivalent), use a unified diff in `kc/patches/`. The patched files are never committed in their patched form (the tree outside `kc/` stays identical to upstream), so write a patch from the working tree:

```bash
patch -p1 < kc/patches/<name>.patch        # existing patch only: start from its current result
$EDITOR app/frontend/...                   # make the change in the upstream file
git diff -- <file> [<file>...] > kc/patches/<name>.patch
git checkout -- <file> [<file>...]         # leave the upstream file untouched
git apply --check kc/patches/<name>.patch  # must apply exactly
```

The build-time `apply-patches.sh` script applies the patches before asset compilation. Ordinary drift after a fork sync is fixed with `bash kc/script/heal-patches.sh` (see "How It Works"); when that reports a conflict, re-implement the change against the new upstream code and write the patch again.

When upstream fixes what a patch worked around, move the patch to `kc/patches/retired/` (the scripts only read `kc/patches/*.patch`, so it is no longer applied).

**Releases:** the KC version lives in `kc/VERSION` and the changes in `kc/CHANGELOG.md` (upstream's root `VERSION`/`CHANGELOG.md` stay untouched so fork syncs never conflict). Bump +0.0.1, add a changelog entry and push an annotated `vX.Y.Z` tag; the GitLab tag pipeline (`kc/gitlab-ci.yml`) builds `zammad-kc:X.Y.Z` into the GitLab registry (`gitlabreg.kawa.link/dean/zammad-kc/zammad-kc`; nothing is pushed to GHCR). Tag only a commit whose `develop` pipeline is fully green, and deploy only an image whose pipeline passed `boot-test-legacy-ui`.

### Key Rules

1. **Never create a file in `kc/` that has the same path as an upstream Zammad file**: `rsync --ignore-existing` never overwrites an upstream file, so the KC file would not be used. `apply-overlay.sh` detects the collision and fails the build.
2. **Always use the `Kc::` namespace** for new Ruby classes.
3. **Register every concern prepend in `kc_loader.rb`**: it's the single source of truth for what KC modifies upstream.
4. **Keep `kc/` self-contained**: only `Dockerfile` and `script/build/cleanup.sh` are modified outside `kc/`, and those edits MUST be **additive-only** (insert new lines; never change or delete an existing upstream line). This guarantees they share no line with upstream, so the GitHub "Sync fork" button never hits a merge conflict. If you need a build tool (e.g. `rsync`), install it in a separate additive KC `RUN` block, do not append to an upstream `apt-get` line.
5. **Never directly edit upstream frontend files**: use `kc/patches/` for modifications to existing upstream TypeScript/Vue files. New KC frontend files go in the overlay and are discovered via `import.meta.glob`.
6. **Verify sync safety before/after every fork sync**: run `kc/script/check-sync-safety.sh --fetch`. It simulates the upstream merge (`git merge-tree`) and fails if any out-of-`kc/` upstream file is modified non-additively or any unsanctioned upstream file is touched. Exit 0 = the Sync button will merge cleanly. Note: `.dockerignore` excludes `.git/`, so `git apply --3way` is NOT available at build time, patches rely on plain `patch`. That is why patches must apply exactly before the build (`verify-patches`).
